# ארכיטקטורת תתי-סוכנים מאובטחת במינימום משאבים — מחקר והמלצות

**מאת:** nova · **תאריך:** 2 ביולי 2026 · **עבור:** דניאלה → אליה
**שיטה:** 4 צירי מחקר מקבילים ברשת (בידוד קל-משקל; ארכיטקטורות multi-agent ו-Claude Agent SDK; NanoClaw והקהילה; דפוסי multi-tenant hosting). מקורות מקושרים לאורך המסמך. סימנתי ⚠️ במקומות שבהם הוודאות חלקית.

---

## תקציר מנהלים

**הממצא המרכזי:** אף פרויקט רציני בתחום לא מריץ קונטeiner מלא לכל *זהות* של סוכן. הדפוס שאליו התכנסה כל התעשייה (Anthropic, Letta, OpenHands, Cloudflare, E2B) הוא:

> **"סוכן = דאטה, Runtime = משותף; בידוד קשיח לפי תחום-אמון (משתמש), לא לפי סוכן."**

כלומר: זהות הסוכן, הזיכרון וה-CLAUDE.md הם קבצים/שורות DB. הבידוד הקשיח (קונטיינר/microVM) נדרש **פעם אחת פר משתמש** — לא פר סוכן ולא פר תת-סוכן. תתי-סוכנים בתוך תחום-האמון של אותו משתמש הם כמעט בחינם.

**שלוש התובנות המעשיות:**
1. **תתי-סוכנים דרך ה-SDK עולים ~0 בתשתית.** ה-Agent tool של Claude Agent SDK יוצר קונטקסט-שיחה נפרד באותו תהליך — לא קונטיינר. `create_agent` (קונטיינר מלא, ~200MB) צריך להישמר רק לסוכני-לוואי פרסיסטנטיים שבאמת צוברים זיכרון לאורך זמן.
2. **הבעיה האמיתית היא ה-95% idle, ולה יש פתרון זול:** provisioning עצל + freeze/reclaim/zram + wake-on-message מעלים את הצפיפות פי 5–20 על אותו VM, בלי לגעת במודל הבידוד.
3. **פער בין ההבטחה למציאות:** "שרת מבודד ששייך רק למשתמש" אינו תיאור הגון של קונטיינר Docker על VM משותף (kernel משותף). או לנסח מחדש, או לעבור ל-microVM — שתי האופציות סבירות.

## חלק 1 — ממצאי המחקר החיצוני

### 1.1 מה תת-סוכן ב-Claude Agent SDK באמת (מתועד)

- Subagent = **קונטקסט LLM טרי באותו תהליך runtime** ([docs](https://code.claude.com/docs/en/agent-sdk/subagents)). רק ההודעה הסופית חוזרת להורה; קריאות הביניים לא מנפחות את הקונטקסט של הסוכן הראשי.
- ידיות שליטה פר-subagent: `tools`/`disallowedTools` (least-privilege), `model` (למשל Haiku לעבודה מכנית), `effort`, `maxTurns`, `background`, קינון עד עומק 5, resume לפי `agentId`.
- `isolation: "worktree"` = בידוד התנגשויות-קבצים בלבד (git worktree), **לא** גבול אבטחה.
- ⚠️ "אותו תהליך, אותו filesystem, אותם הרשאות" — מרומז חזק בתיעוד אך לא נאמר מילולית; כל הראיות (ירושת כלים, transcripts משותפים) תומכות.
- עלות טוקנים: Anthropic עצמה מדווחת שמערכות multi-agent צורכות **פי ~15** טוקנים משיחה רגילה ([מקור](https://www.anthropic.com/engineering/multi-agent-research-system)) — הבקרה היא model tiering, effort, הגבלת עומק ו-maxTurns.

### 1.2 המודל השכבתי המוסכם בתעשייה (2025–2026)

| שכבה | מה נמצא בה | רמת בידוד נדרשת |
|---|---|---|
| **לולאת הסוכן** (LLM loop, זהויות, זיכרון, ערוצים, תזמון) | דאטה + קריאות API | ניתנת למולטיפלקס בבטחה; לא מחזיקה סודות גולמיים |
| **הרצת כלים** (bash, קוד, MCP) | הקוד שהסוכן מריץ בפועל | Sandbox קשיח — **פר משתמש/סשן**, לא פר סוכן |
| **סודות ו-egress** | קרדנשיאלס, יציאה לרשת | תמיד **מחוץ** לכל sandbox: פרוקסי מזריק-קרדנשיאלס + allowlist דומיינים |

- Anthropic בעצמה: sandbox-runtime (srt, bubblewrap) ל-Bash בלי קונטיינר; העיקרון המוצהר — "בידוד filesystem **וגם** רשת, אחרת אין ערך" ([מקור](https://www.anthropic.com/engineering/claude-code-sandboxing)). ב-Claude Code on the web הקרדנשיאלס יושבים בפרוקסי מחוץ ל-sandbox.
- דוגמאות: OpenHands — קונטיינר **פר שיחה** (לא פר סוכן), לולאת הסוכן בחוץ; Letta — סוכן = שורות Postgres, שרת stateless משותף; Cloudflare Agents — actor פר משתמש שישן בחינם כשאינו פעיל.
- **OneCLI vault שכבר יש לנו = בדיוק הדפוס המומלץ לשכבת הסודות.** זה נכס, לשמר.

### 1.3 טכנולוגיות בידוד קל-משקל — טבלת הכרעה

| טכנולוגיה | תקורת RAM | בידוד | דרישות | מתאים לנו? |
|---|---|---|---|---|
| Docker מוקשח (userns, seccomp, cap-drop, pids-limit, quotas) | ~0 | kernel משותף — טוב נגד תאונות, לא נגד תוקף עם kernel 0-day | כלום | הבסיס המיידי |
| **gVisor (runsc)** | ~30MB/sandbox ⚠️(מספר צד-ג') | חזק — kernel אפליקטיבי ב-userspace, שטח תקיפה מזערי | **ללא KVM — עובד על כל VM** | **המועמד המרכזי לשדרוג multi-tenant** |
| Firecracker microVM | <5MiB ל-VMM (+RAM לאורח) , boot ~125ms, restore מ-snapshot ~25–200ms | הזהב — kernel נפרד | **חייב /dev/kvm** — bare metal (Hetzner/OVH) או nested virt (GCP/Azure; AWS רק metal/סדרות 2026 חדשות) | רק אם עוברים ל-bare metal; תפעול כבד (images, רשת, snapshots) |
| Kata Containers | ~50–200MB/pod | VM-grade בממשק OCI | KVM | כבד מדי לשלב הזה |
| nsjail/bubblewrap | ~0 | תלוי-פרופיל; סוכן שמריץ shell שרירותי מחייב פרופיל רחב | כלום | כשכבת עומק בתוך הקונטיינר, לא כגבול יחיד |

**נקודת הכרעה חשובה:** Firecracker דורש KVM — על רוב ה-VMs בענן (בלי nested virt) הוא פשוט לא ירוץ. gVisor עובד בכל מקום ולכן הוא "הבידוד הטוב ביותר לדולר-תפעול" עבורנו.

### 1.4 להפוך idle לזול — הטבלה הקריטית (95%+ מהזמן הסוכנים ישנים)

| טכניקה | CPU בזמן idle | RAM בזמן idle | Resume |
|---|---|---|---|
| `docker pause` (cgroup freeze) | 0 | מלא | מיידי |
| freeze + `memory.reclaim` + **zram/zswap** | 0 | ~RSS÷2–3 (דחוס) או ~0 (לדיסק) | מיידי-בפועל (page faults הדרגתיים) ⚠️ אין benchmark פומבי מקצה-לקצה |
| CRIU checkpoint לדיסק | 0 | 0 | ~100ms–שניות; שברירי (TCP, fds); experimental ב-Docker |
| gVisor checkpoint/restore | 0 | 0 | תת-שנייה; יציב יותר מ-CRIU (ה-"kernel" ב-userspace) |
| Firecracker snapshot | 0 | 0 | ~25–500ms; דורש KVM; זהירות משכפול אנטרופיה |

כל ספקי ה-sandbox המנוהלים (E2B, Fly, Modal, Cloudflare) התכנסו לאותה צורה: snapshot/suspend לאחסון (~$0.15/GB/חודש), resume ב-0.1–1 שניות, חיוב רק בזמן ערות. Fly Machines suspend/resume ("כמה מאות ms", מגבלה: ≤2GB RAM) הוא המקבילה המנוהלת הקרובה ביותר לארכיטקטורה שלנו.

### 1.5 NanoClaw עצמו — מה הקהילה יודעת

- הריפו אומת: [nanocoai/nanoclaw](https://github.com/nanocoai/nanoclaw) (~30k כוכבים, v2.1.17 מ-17.6.2026). נוצר ע"י Qwibit AI כתגובת-אבטחה ל-OpenClaw — **לא** fork שלו.
- README ממצב אותו כ-**single-user/personal — לא תשתית multi-tenant**. אין guidance רשמי על pooling / scale-to-zero / runtime משותף (חיפשתי במפורש — אין).
- עלות מתועדת: **~200MB RAM לקונטיינר**; זמן spawn מזוהה כצוואר בקבוק. Issues רלוונטיים: [#1184](https://github.com/qwibitai/nanoclaw/issues/1184) (תלות קשיחה ב-Docker socket; הצעת provider interface ל-Pods אפמרליים — פתוח), #839 (task containers תקועים 30 דק' עד timeout וחוסמים את התור), #138/#293 (משימות מתוזמנות כפולות/deadlock).
- **הבאגים שלנו מוכרים במשפחה:** ל-OpenClaw יש מחלקת-באגים שלמה של תשובות כפולות ([#33592](https://github.com/openclaw/openclaw/issues/33592), #34039, #37844, #42681 — `deliver()` רץ גם אחרי זיהוי כפילות). PR #2123 ב-NanoClaw מדכא טקסט כפול כש-`send_message` נורה. כלומר: ה-triple-message שלנו הוא כנראה שילוב של (א) חוסר dedupe ב-inbound לפי `update_id` של טלגרם, (ב) חוסר idempotency-key ב-outbound — ושווה לבדוק אם יש fix upstream לפני שמתקנים לבד.
- אירועי אבטחה במשפחה (OpenClaw): 135k מופעים חשופים (SecurityScorecard), prompt-injection חי שהוסיף ערוץ טלגרם של תוקף (Zenity), ו-36% מסקילים ב-ClawHub עם prompt injection (Snyk ToxicSkills). הלקח לפיילוט: ה-blast radius של הודעה נכנסת עוינת הוא הסיכון המרכזי, והסקילים הם וקטור supply-chain.

### 1.6 טלגרם, abuse וצפיפות — ממצאים אופרטיביים

- **טלגרם:** BotFather מוגבל ל-20 בוטים לחשבון — bot-per-user לא סקיילבילי; בוט יחיד עם ניתוב פר-chat הוא הדפוס הנכון (וכבר כך אצלנו). Webhook עדיף על long-polling בסקייל (polling מחייב תהליך תמידי = הורג scale-to-zero; ו-getUpdates כפול מחזיר **409 Conflict** — ייתכן שזה בדיוק מה ששובר לנו inbound ב-double-launch). טלגרם **עושה retry ל-webhooks** — dedupe לפי `update_id` הוא חובה, לא nice-to-have. מגבלות outbound: ~1 הודעה/שנייה לצ'אט, ~30/שנייה לבוט.
- **Abuse בחינמי:** free compute עם egress = מגנט לכורי קריפטו וספאם (TravisCI ו-Sourcehut הרגו free tier בגלל זה; GitLab: אימות כרטיס-אשראי היה הצעד האפקטיבי ביותר). היתרון שלנו: **זהות טלגרם היא כבר אימות-טלפון** — לקשור סוכן אחד ל-user ID אחד מחסל הרבה מהחזית. חדש יחסית: LLM-credit farming — משתמשים שחולבים את חשבון ה-API שלנו ⚠️(מתועד דק, אבל התמריץ זהה לקריפטו).
- **צפיפות:** ב-200MB לקונטיינר, VM של 8GB מכיל ~15–40 סוכני idle בלבד; 32GB ~70–170 (אריתמטיקה, לא benchmark). עם lazy-start הקיבולת נגזרת מ*פעילים בו-זמנית* (בד"כ 1–5% מהנרשמים) — קפיצה של סדר גודל.

## חלק 2 — הערכת מצב נוכחי וסיכונים

**מה טוב בארכיטקטורה הקיימת (לשמר):**
- OneCLI vault — קרדנשיאלס מחוץ לקונטיינר, מוזרקים בזמן-בקשה = בדיוק ה-best practice.
- קונטיינר-פר-משתמש כגבול tenant — המודל הנכון עקרונית; הבעיה היא רק ש*כל* הקונטיינרים ערים תמיד.
- ערוץ יחיד בטלגרם, ניתוב פר-chat, tunnel קבוע — צורה נכונה.

**סיכונים, מסודרים לפי חומרה:**

1. **Provisioning בזמן הרשמה = וקטור DoS-על-הארנק.** `POST /api/register` ציבורי שמרים קונטיינר מלא מיידית: סקריפט הרשמות ממלא את ה-VM תוך דקות, בחינם לתוקף. (חומרה: גבוהה, ניצול טריוויאלי.)
2. **אין (ככל הנראה) מגבלות egress ו-quota פר-סוכן.** סוכן חופשי עם רשת = פלטפורמת קריפטו/ספאם/חליבת-API בחינם. זה מה שהרג free tiers מתועדים.
3. **פער ההבטחה:** "שרת מבודד ששייך רק למשתמש" מול קונטיינר על kernel משותף. הנורמה בשוק (E2B, KiloClaw) היא לנקוב במנגנון ("Firecracker microVM, kernel ייעודי"). הסיכון כרגע תדמיתי/חוזי — לא מצאנו אכיפה רגולטורית בתחום — אבל לפיילוט שמוכר "מאובטח לחלוטין" זה חשוב.
4. **Prompt injection דרך הודעות נכנסות** — הסיכון המבצעי המרכזי במשפחת המוצרים הזו (הודגם חי ב-OpenClaw). ה-blast radius אצלנו מוגבל ע"י הקונטיינר וה-vault (טוב!), אבל אין allowlist דומיינים ל-egress מהקונטיינר.
5. **תקרת צפיפות קשיחה:** ב-200MB×always-on, ה-VM נחנק אחרי עשרות בודדות של נרשמים — צוואר הבקבוק שאליה זיהה, מאושש מספרית.
6. **שבירויות ידועות:** triple-message (מחלקת באגים מוכרת upstream), כלל מופע-יחיד (עקבי עם 409 של getUpdates כפול או שני writers על SQLite), SPOF יחיד (VM אחד + tunnel אחד).

## חלק 3 — המלצות מתועדפות

### עדיפות 0 — תיקונים מיידיים (ימים, סיכון אפסי)

| # | מה | איך | Tradeoff |
|---|---|---|---|
| 0.1 | **תיקון triple-message** | Dedupe ב-inbound לפי `update_id` (SETNX/טבלה עם TTL שעה) + idempotency-key ב-outbound (hash של session+turn) + ACK מיידי ועיבוד אסינכרוני. לבדוק קודם fix upstream (PR #2123 ומשפחת ה-issues ב-OpenClaw) | אין. חובה לפני כל scale |
| 0.2 | **אכיפת מופע-יחיד** | systemd unit עם `Restart=always` + flock/PID-lock על שירות ה-provision; לוודא writer יחיד ל-inbound.db. אם ב-polling — לשקול מעבר ל-webhook (מבטל את בעיית ה-409 מבנית) | אין |
| 0.3 | **שם ידידותי לסוכן** | בזמן provision: לגזור שם מהפרופיל (או מחולל שמות קצר) ולכתוב ל-CLAUDE.local.md של הסוכן החדש; ה-slug נשאר מזהה פנימי | אין |
| 0.4 | **Provisioning עצל** | בהרשמה: רשומת DB + קוד צימוד בלבד. הקונטיינר קם **בהודעה הראשונה בטלגרם**. הרשמה-זבל עולה ~0; זהות הטלגרם מאומתת לפני שמוקצה חומרה | דקת-ההקמה זזה להודעה הראשונה (עדיין <דקה); שינוי קטן ב-flow |

### עדיפות 1 — שיטת תתי-הסוכנים (הלב; שבוע-שבועיים, בעיקר מדיניות וקונפיגורציה)

**ההמלצה: מודל שלוש שכבות. תת-סוכן הוא ברירת-מחדל *בתוך* הקונטיינר של המשתמש, לא קונטיינר חדש.**

1. **תתי-סוכנים סטייטלס = SDK subagents (Agent tool) בלבד.** מחקר, סריקות, משימות מקביליות — קונטקסט LLM נפרד באותו קונטיינר. עלות תשתית ~0; הבידוד ירושה מהקונטיינר של המשתמש — וזה *נכון* אבטחתית, כי תת-הסוכן פועל באותו תחום-אמון. מדיניות עלות-טוקנים: model tiering (Haiku/Sonnet למשימות מכניות), `effort` נמוך כברירת-מחדל, `maxTurns`, חסימת קינון מעבר לעומק 2 (להסיר Agent מכלי הילדים).
2. **סוכנים פרסיסטנטיים = `create_agent` רק כשיש הצדקה של זיכרון מצטבר**, ותמיד בתוך מכסה פר-משתמש (למשל: עד 2 סוכני-לוואי). כל סוכני המשתמש חולקים את תחום-האמון שלו — אין צורך בבידוד ביניהם, רק בינם לבין משתמשים אחרים.
3. **הקשחת שכבת הרצת-הכלים בתוך הקונטיינר:** bubblewrap/srt סביב Bash + **allowlist דומיינים ל-egress** (הכל ממילא עובר OneCLI proxy — לאכוף שם default-deny עם רשימת שירותים מותרים). זה מקטין את ה-blast radius של prompt injection מ"כל מה שהקונטיינר יכול" ל"רשימת יעדים מאושרת".

**למה:** משיג "ריבוי סוכנים" בלי אף קונטיינר נוסף, עקבי עם הדפוס שכל התעשייה התכנסה אליו, ומחזק אבטחה במקום להחליש. **עלות:** בעיקר מדיניות ב-CLAUDE.md/קונפיג + עבודת proxy. **Tradeoff:** תתי-סוכנים צורכים טוקנים (עד פי 15 משיחה) — לכן ידיות העלות הן חלק מההמלצה, לא תוספת.

### עדיפות 2 — צפיפות: idle צריך לעלות ~0 (שבועיים-שלושה)

- **Wake-on-message:** ה-gateway (תהליך קטן always-on) מקבל webhook → תור פר-משתמש עם debounce של 1–3 שניות → מעיר את הקונטיינר → מרדים אחרי N דקות idle. התור הקיים (inbound.db) הוא כבר חצי מהפתרון.
- **מדרג הרדמה:** 0–10 דקות ער → freeze (`docker pause`) + `memory.reclaim` ל-**zram** → אחרי שעות, checkpoint לדיסק (או פשוט stop אם ה-state כולו על disk volume). Resume מ-freeze מיידי; מ-stop — שניות בודדות.
- **גדרות פר-קונטיינר:** memory limit + `--max-old-space-size` מתחתיו, CPU shares, pids-limit, disk quota.
- **אפקט:** מ~15–40 סוכנים ל-8GB → מאות (הקיבולת נגזרת מפעילים בו-זמנית). **Tradeoff:** מורכבות supervisor; חיבורים חיים (long-polling פנימי) מתנתקים בהרדמה — ה-runtime צריך reconnect נקי (עוד סיבה ל-webhook). ⚠️ מספרי הדחיסה של zram הם הערכה הנדסית, לא benchmark — למדוד על עומס אמיתי לפני התחייבות לקיבולת.

### עדיפות 3 — שדרוג בידוד + יישור ההבטחה (חודש±, החלטה אסטרטגית)

שתי אופציות כנות, לפי התשתית:
- **3א. gVisor (מומלץ כברירת-מחדל):** `--runtime=runsc` על הקונטיינרים הקיימים — שינוי קונפיגורציה כמעט בלבד, עובד על כל VM בלי KVM, מקטין דרמטית את שטח התקיפה בין דיירים. עלות: ~30MB/sandbox + 0–30% תקורת syscalls (הצד הכבד — npm installs וכד'). Modal מריצים על זה 20k+ קונטיינרים בו-זמנית. במקביל — **לנסח מחדש את ההבטחה**: "סביבת סוכן מבודדת משלך — קונטיינר ייעודי, זיכרון ו-filesystem פרטיים, sandbox ברמת kernel" (הגון וגם נשמע טוב).
- **3ב. microVM אמיתי (אם רוצים לעמוד ב"שרת משלך" מילולית):** מעבר ל-bare metal (Hetzner/OVH) עם Firecracker + snapshots, או offload ל-Fly Machines (suspend/resume, idle = $0.15/GB/חודש) — ואז אפשר לומר בכנות "VM ייעודי עם kernel משלו", כמו E2B ו-KiloClaw. עלות: תפעול משמעותי (images, רשת, היגיינת snapshots) או תלות בספק. לא דחוף לפיילוט — כן רלוונטי לגרסה בתשלום.

### עדיפות 4 — הקשחת חזית ההרשמה (במקביל, ימים)

מדרג חיכוך: אימות אימייל + Turnstile בדף הנחיתה → rate-limit פר-IP/ASN על `/api/register` → **סוכן אחד פר Telegram user ID** (האימות-טלפון של טלגרם עובד בשבילנו) → מכסות פר-סוכן: טוקנים/יום, CPU, דיסק, egress → התראת CPU-גבוה-בזמן-idle (חתימת כרייה) → kill switch: suspend מיידי פר-סוכן + דגל הקפאת-provisioning גלובלי.

## סיכום — סדר הפעולה המוצע

1. **עכשיו:** 0.1–0.4 (באגים + provisioning עצל) — משחרר את הפיילוט לצמוח בלי להישבר.
2. **הלב:** מודל שלוש-השכבות לתתי-סוכנים — SDK subagents כברירת-מחדל, `create_agent` במכסה, egress allowlist ב-OneCLI. עונה ישירות לשאלת אליה: *הבידוד פר-משתמש, הריבוי פר-קונטקסט.*
3. **צפיפות:** wake-on-message + freeze/zram — פי 5–20 קיבולת על אותו ברזל.
4. **אסטרטגי:** gVisor + ניסוח-מחדש של ההבטחה (או Firecracker/Fly אם הולכים על "שרת משלך" מילולית).

**מה בדקתי ולא מצאתי (בכנות):** אין guidance רשמי של NanoClaw ל-multi-tenancy או pooling — אנחנו בשטח לא-סלול מבחינת upstream (issue #1184 הוא הכיוון היחיד, פתוח); אין benchmark פומבי ל-freeze+zram מקצה-לקצה; מספרי ה-RAM של gVisor/Kata הם מדידות צד-שלישי; דיוני הדיסקורד של NanoClaw לא אינדקסו ברשת — הממצאים מגיעים מ-docs, issues וניתוחי צד-שלישי.
